# Auto Monitor Bot — полный аудит скорости и полноты

Дата: 2026-09-03
Рабочая модель: бесплатный laptop-first runtime; намеренная остановка и выключенный ноутбук не считаются аварией. После запуска приоритет всегда у realtime, а пропущенное offline-окно восстанавливается в фоне до сохранённой границы.

## Итог

Текущая оценка: **8.4/10** для локального laptop-first решения.

| Область | Оценка | Вывод |
|---|---:|---|
| Realtime-архитектура | 9.0/10 | Два hot-worker, лидерская аренда, отдельный background-worker и приоритет realtime устранили общую hot-точку отказа. |
| Восстановление offline-окна | 9.2/10 | Граница хранится durable, backfill продолжает с курсора, имеет overlap и теперь закрывает окно только доказуемо. |
| Доставка Telegram | 8.8/10 | Durable journal, глобальный rate gate, inline fast send и flash bundle защищают первую ссылку при burst. |
| Наблюдаемость | 8.6/10 | Есть timestamps request start → first byte → candidate → journal → Telegram acceptance и разбивка по источникам. |
| Реальная полнота источников | 5.5/10 | Главный предел находится вне приложения: публичные индексы запаздывают, RST защищён CAPTCHA, часть агрегаторов не отдаёт точное время. |
| Автотесты критического контура | 6.5/10 | 316 тестов и сильные pure-policy тесты, но orchestration/processor всё ещё почти не покрыт интеграционно. |

Нельзя честно гарантировать «всегда первый» и абсолютный ноль пропусков: официальный OLX API не даёт доступ к объявлениям других пользователей, поэтому поиск зависит от публичных страниц/индексов и их задержек. Это подтверждает [официальный FAQ OLX](https://developer.olx.ua/ua/articles/faq). Внутренний путь можно ускорять и делать доказуемым; момент появления карточки в публичном индексе приложение не контролирует.

## Архитектура после исправлений

1. API и dashboard управляют состоянием и показывают доказательства, но не выполняют тяжёлый сбор.
2. Два hot-worker работают как leader/standby. Потеря одного процесса не останавливает realtime.
3. Background-worker обслуживает `collector.coverage`, `collector.backfill`, enrichment и проверки, не удерживая hot run.
4. Redis/BullMQ хранит приоритетные durable-задачи. Recovery получает стабильный deduplication ID на источник, поколение мониторинга и окно. Это соответствует BullMQ Simple Mode: пока задача не завершена, новая с тем же ID не добавляется ([BullMQ](https://docs.bullmq.io/guide/jobs/deduplication)).
5. PostgreSQL хранит наблюдения, курсоры, recovery-окна, frozen anchors, уведомления и аудит.
6. Telegram сначала принимает ссылку/flash bundle, а подробное обогащение идёт следом. Это важно, потому что Telegram рекомендует не превышать примерно одно сообщение в секунду в одном чате ([Telegram Bots FAQ](https://core.telegram.org/bots/faq)).

## Исправленные дефекты этого аудита

### P0 — ложное доказательство offline recovery

Обнаружено: пустая первая OLX-страница могла закрыть окно как `EXHAUSTED`; позднее realtime мог закрыть его как `CUTOFF` без сохранённой даты, реально достигшей границы.

Исправлено:

- пустая первая страница больше не является доказательством исчерпания;
- `CUTOFF` принимается только если `oldestObservedAt <= requiredCutoffAt`;
- timestamp доказательства записывается атомарно в recovery window;
- realtime не нейтрализует свежие sticky-карточки; это разрешено только recovery-backfill;
- старые неверные `EXHAUSTED`/`CUTOFF` доказательства автоматически переоткрываются миграциями;
- anchors восстанавливаются только из наблюдений, существовавших до `persistedBoundaryAt`.

### P0 — recovery каждый раз начинал с первой страницы

Исправлено:

- следующий bounded attempt продолжает с `lastPage`;
- две крайние страницы перекрываются, чтобы компенсировать смещение offset-feed при поступлении новых объявлений;
- page/request/observation counters накапливаются за всё окно, а не перезаписываются последней попыткой;
- после доказанного закрытия cursor сбрасывается.

### P0 — дубли recovery-задач

Исправлено: BullMQ deduplication удерживает максимум одну незавершённую задачу на конкретное recovery-окно. В живой проверке очередь не накопила waiting-дубликатов.

### P0 — сомнительный protection probe снимал защиту

Исправлено: короткий/пустой OLX-ответ после CAPTCHA или rate limit больше не переводит источник в ACTIVE, не двигает success boundary и не закрывает incident. Пауза продлевается штатно. Агрессивных повторов и обхода CAPTCHA нет.

### Toolchain и supply chain

- pnpm обновлён с 10.0.0 до 10.34.5;
- `overrides` перенесены в корневой `pnpm-workspace.yaml`, где pnpm 10 действительно читает project settings ([pnpm settings](https://pnpm.io/10.x/settings));
- уязвимый transitive `mysql2` закреплён на 3.24.3, Fastify обновлён до 5.12.1, а `fast-uri` — до 3.1.6/4.1.3;
- production audit не находит известных high-risk уязвимостей;
- isolated build сохраняет исходный `next-env.d.ts` и больше не загрязняет checkout.

## Измеренная задержка

Снимок 24-часового окна после проверки; это смешанный интервал с перезапусками, recovery и burst, а не только steady state.

| Этап OLX | p50 | p95 |
|---|---:|---:|
| request start → first byte | 1.919 s | 2.393 s |
| first byte → hot candidate | 1.155 s | 2.900 s |
| hot candidate → durable journal | 9 ms | 796 ms |
| durable journal → Telegram acceptance | 564 ms | 4.767 s |
| request start → Telegram acceptance | 3.816 s | 9.826 s |

Главные внутренние резервы теперь находятся не в PostgreSQL и не в очереди, а в разборе ответа/нормализации и в burst-доставке Telegram. PostgreSQL на живом runtime отвечал примерно за 1 ms, pool не имел waiting/retry/exhaustion.

Наблюдаемая source publication → detection значительно хуже: OLX p50 около 24.6 минуты, p95 около 2.52 часа. Разбивка канала также показывает десятки минут на публичных HTML/API feed. Это не означает, что сам worker столько обрабатывает: это разница между временем, которое сообщил источник, и моментом, когда запись появилась в доступном нам публичном канале.

## Оставшиеся слабые места и лучший следующий порядок

### P0 — недостижимая граница публичного offset

OLX ограничивает публичное смещение; текущий предел конфигурации — 1000 элементов. Если offline-окно содержит больше доступного хвоста, backfill не сможет честно доказать границу. Сейчас он оставляет окно pending, что безопаснее ложного `VERIFIED`, но может периодически повторять дорогой deep scan.

Следующий апгрейд: добавить статус `UNRESOLVED`, отдельное alert-событие, backoff и ручное подтверждение причины. Realtime должен продолжать работать; повторный deep scan — только после нового сигнала или увеличенного безопасного окна.

### P1 — AUTO.RIA фильтр слишком широкий

У активного фильтра нет официального `autoRiaMarkId`; planner помечает это как danger и оценивает проход в 11 запросов. Это быстро расходует часовую квоту и всё равно не даёт качественного широкого realtime.

Лучшее решение: либо задать конкретные официальные ID марок/моделей, либо исключить AUTO_RIA именно из этого широкого фильтра и завести отдельные узкие фильтры. Самостоятельно менять пользовательский охват нельзя — это может создать реальные пропуски.

### P1 — низкое интеграционное покрытие orchestration

Общее line coverage около 32%; `collector-run.ts` остаётся практически без прямого интеграционного покрытия. Pure-policy тесты сильные, но именно связка DB transaction → queue → source status → notification содержит самые дорогие ошибки.

Лучший апгрейд: test harness с временной PostgreSQL schema и Redis namespace, fake collector и сценариями:

- realtime во время recovery;
- crash между journal и queue enqueue;
- duplicate job и повторная доставка;
- protection probe с пустым ответом;
- restart с persisted pending window;
- offset ceiling без ложного verification.

### P1 — p95 Telegram при burst

Flash bundle уже даёт все свежие ссылки первым сообщением, но подробные карточки физически сериализуются rate gate. Нужно отдельно показывать `first-link acceptance` и `last-detail acceptance`, не смешивая их в один p95. Для цели «узнать первым» главным SLO должен быть первый показатель.

### P1 — источник RST защищён CAPTCHA

RST остаётся `CAPTCHA_DETECTED` и корректно поставлен на паузу. Обход защиты, fingerprint spoofing, CAPTCHA-solving и агрессивная ротация IP не являются качественным ускорением: они повышают вероятность длительной блокировки и юридический риск. Безопасные варианты — официальный доступ/разрешённый feed, ручная проверка в браузере или независимый легальный агрегатор с измеряемым canary.

### P1 — слабая точность времени AutoMoto/RST

AutoMoto отдаёт день без точного времени и не гарантирует строгую newest-first сортировку; RST также не даёт надёжный timestamp. Эти источники полезны для coverage, но не должны участвовать в сравнении секундного realtime SLO наравне с OLX/AUTO.RIA/Cars.ua.

### P2 — остановка процессов не является queue drain

При принудительном развёртывании активная BullMQ-задача может стать `stalled`, после чего штатно восстанавливается. Это не потеря данных, но создаёт шум и задержку до recovery. Нужен graceful shutdown: сначала прекратить scheduler, дождаться active jobs с верхним timeout, закрыть workers/Redis connections и только затем завершить процессы.

### P2 — maintenance и зависимости

- не обновлять major-зависимости «ради свежести» без benchmark/regression gate;
- включать более агрессивный per-table autovacuum только при росте dead tuples/latency — текущая база мала и здорова;
- добавить supply-chain policy (`minimumReleaseAge`/trusted dependencies) после отдельной проверки совместимости.

## Вывод

Внутренний контур теперь быстрый и гораздо строже защищён от скрытых пропусков: приложение сначала фиксирует объявление, сохраняет доказательство и отправляет первую ссылку, а тяжёлую работу отодвигает. Самый сильный дальнейший прирост даст не уменьшение пары миллисекунд в БД, а: (1) явный `UNRESOLVED` для недостижимого публичного хвоста, (2) узкие AUTO.RIA планы, (3) интеграционные crash/restart тесты и (4) раздельный SLO первой ссылки и последней подробной карточки.
