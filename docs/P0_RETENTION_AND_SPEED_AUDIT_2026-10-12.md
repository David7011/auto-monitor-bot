## Что исправлено в P0

Отправка карточки сохраняла `DELIVERED`, а retention при финализации признавал только `SENT/UPDATED`. Telegram уже очищался, но запись оставалась с `messageId` и просроченным сроком. После backoff она снова попадала в обработку.

Теперь выборка, захват и финализация используют один набор доставленных статусов: `SENT`, `UPDATED`, `DELIVERED`. Недоставленные, неоднозначные и карантинные записи не очищаются этим путём.

После успешной очистки обнуляются `messageId`, сроки и признаки активной политики/избранного. Статус доставки, `sentAt` и `acceptedAt` сохраняются: очищенный receipt продолжает защищать от повторной отправки. Объявление удаляется только тогда, когда все его receipts завершили очистку. Уведомление другого получателя с действующим сроком, избранным или незавершённой доставкой удерживает объявление.

При окончательном удалении сохраняется компактный `SourceSeenListing` с `decision=NOTIFIED`. Счётчики preview/health не считают очищенные receipts просроченным legacy. CLI продолжает проходы, даже если пачка только очистила receipts, сохранив объявления для других получателей.

В ранее подготовленном патче сроки обнулялись без обнуления `favoritedAt/retentionPolicyAppliedAt`. Это несовместимо с CHECK-ограничениями из миграции `20260722_zz_listing_retention_constraints`. Исправлено до выпуска. Отдельно обнаружено, что CHECK-ограничений на `telegram_notifications` в текущей базе фактически нет; изменения схемы в этом этапе не выполнялись.

## Следующие этапы, в порядке ожидаемой пользы

### P1.1 — убрать влияние платной API-квоты на public polling AUTO.RIA

**Подтверждено кодом и runtime.** `monitoring/control.ts:autoRiaLiveIntervalSeconds()` вычисляет `max(LIVE_AUTO_RIA_MIN_INTERVAL_SECONDS, ceil(3600/AUTO_RIA_HOURLY_REQUEST_LIMIT))` без проверки public/api. При лимите 30 запросов/час это 120 секунд. В public режиме такой интервал затем сохраняется в source, хотя минимум LIVE задан 60 секунд. Реальный p50 между сканами — 120,066 секунды.

Предложение: выбирать интервал по access mode; public использует собственный интервал и собственную защиту от rate limit, official API сохраняет квоты и расчёт количества контекстов. Это способ убрать до минуты ожидания следующего опроса; при равномерном появлении объявлений ожидаемое среднее ожидание опроса уменьшается примерно с 60 до 30 секунд. Это оценка для polling, а не обещание publication→delivery.

Проверка: public с quota=30 получает 60 с; API с quota=30 остаётся ограничен; несколько контекстов не превышают API-бюджет. Затем сравнить фактические интервалы, новизну и защитные ответы. Понижение интервала public до 60 секунд ещё не применялось.

### P1.2 — разобраться с 440 UNRESOLVED OLX recovery windows

**Подтверждено:** в снимке 440 окон `UNRESOLVED/UNSTABLE_PAGINATION`, 190 `VERIFIED`, одно `PENDING`. Недавние незакрытые окна создавались с интервалами в несколько минут. В окне измерений BACKFILL: 1539 запусков, 1006 запросов, 0 new; COVERAGE: 460 запусков, 732 запроса, 0 new. Нулевой new не доказывает бесполезность покрытия: его задача также доказать отсутствие пропусков.

Предложение: проверить создание повторных/перекрывающихся окон на один fingerprint и общий незакрытый диапазон; объединять требования к cutoff в существующее окно, сохраняя происхождение и доказательства. Исследовать, почему ordered overlap не удаётся проверить на HTML-first ленте. Критерии JSON-offset recovery должны соответствовать фактическому формату HTML evidence. Окно с неизвестной полнотой сохранять незакрытым до настоящего доказательства.

Проверка: обновления головы между двумя страницами, исчезновения объявлений, sticky listings, дубликаты, смена capability generation, перезапуск, пустая страница и offset ceiling. Снизить число повторных запросов на доказанный прогресс, одновременно сохранив обнаружение всех тестовых объявлений. Причина каждой из 440 записей индивидуально ещё не доказана.

### P1.3 — ускорить передачу OLX-кандидата после готового ответа

**Подтверждено:** parsed→hot p95 5,220 с при p50 20 мс; есть хвост ожидания, не объясняемый временем JSON/HTML parse. Early handoff уже реализован через `onHotCandidates`, поэтому предложение «просто добавить early handoff» ничего не улучшит.

Разделить трассы по observationChannel/requestId, числу целей, HTML hydration и пути ранней/финальной передачи. Проверить, где готовый feed ждёт других операций. Обработать кандидата после минимально достаточного ответа; остальные данные дополнять после durable handoff. Не ставить Telegram ожидание и позднее обогащение в зависимость готовности следующего feed. На всём пути сохранить PostgreSQL до Redis claim/queue.

Цель следующего опыта: parsed→hot p95 менее 0,5 с для полностью распарсенного самостоятельного feed без detail hydration; цель требует проверки, а не гарантирована. OLX origin остаётся сериализованным.

### P1.4 — ограничить длинные хвосты Telegram, не уменьшая gate 1100 мс

**Подтверждено:** в отдельных карточках filter→Telegram request 42–44 секунды; HTTP принятие одного запроса достигало 17,876 с. В основном realtime-наборе p95 dispatch wait ~1,979 с. Длинные случаи относятся к старой истории, поэтому их нельзя автоматически приписать текущему релизу или объявить постоянным регрессом.

Разделить причины: ожидание gate, retry_after, фотоальбом и долгий Bot API request. Для первой реакции оставлять короткую ссылку/flash header; фотографии и подробную карточку догружать после принятия первой реакции. Flash уже включён (2–20 объявлений), менять нужно его поведение при burst и хвост за лимитом. Проверить, что задержка oversized tail 5 с оправдана порядком и не применяется лишний раз.

Проверка: bursts 2/20/21/100, несколько получателей, 429, timeout после фактического принятия, падение после отправки до DB persist. Не повторять неоднозначный send без lease: у Telegram send нет клиентского idempotency key в используемом пути.

### P1.5 — сделать измерение «обнаружено» однозначным

**Подтверждено кодом:** normalizers сохраняют `firstSeenAt=now`, где `now` передаётся из скана. В реальных строках `firstSeenAt` бывает раньше `requestStartedAt` на 5–15 секунд. Это время начала скана/первого наблюдения по текущему контракту, а не точный момент готовности кандидата.

Разнести `scanStartedAt`, фактическое появление кандидата и durable first observation. Существующий `firstSeenAt` участвует в freshness и dedupe — менять его смысл без миграционного анализа нельзя. Основной SLA реакции считать от `hotCandidateAt`/фактического candidate event; отдельно показывать HTTP, polling и source timestamp lag. Добавить аналогичную трассу для AUTO.RIA public. Иначе оптимизация способна улучшить только цифру, не поведение.

## P2 — полезные улучшения и удаление лишней работы

1. **Пакетная очистка Telegram.** Сейчас каждый ID альбома проходит отдельный delete, а после ограничения по возрасту — ещё text/caption fallback. Это делает разовую очистку хвоста долгой. Рассмотреть `deleteMessages` для 1–100 ID одного чата, с условной DB-финализацией каждого receipt и индивидуальным fallback на ошибках/старых сообщениях. API пропускает отсутствующие сообщения, но сохраняет ограничения удаления: [официальная документация](https://core.telegram.org/bots/api#deletemessages). Экономия числа запросов не означает разрешение повысить общую частоту. Текущую очистку ради этой оптимизации не меняли.

2. **Убрать заведомо неудачный delete для старых сообщений.** Если известный `sentAt` уже вне окна удаления обычных сообщений, сразу выбирать допустимый edit/tombstone путь. Проверить разновидности сообщений и fallback; не считать старое сообщение физически удалённым при одном только edit. Это снижает число API round trips в старом хвосте.

3. **Сократить повторные enrichment/update.** Telegram update заново вызывает seller phone lookup; cache помогает, но concurrent lookup может продублировать origin request. Проверить single-flight на source/externalId, объединять market/phone/vehicle updates по listing+recipient и отбрасывать update с неизменившимся содержимым. Не переносить phone/market на первую отправку.

4. **Бюджет market research по полезности.** Поиск рыночных аналогов делает отдельные OLX ENRICHMENT-запросы. Уже есть cache и lock. Настроить reuse по близким параметрам, остановку при достаточной качественной выборке и разрешение stale cache, когда realtime/recovery заняты. Уменьшать источниковую нагрузку, сохраняя смысл оценки.

5. **Windows HTTP: измерить IPC/декодирование.** Используется постоянный PowerShell helper с Base64 JSON, Buffer, Response и последующим чтением. У OLX body→parsed p50 234 мс; decoding p50 188 мс. Добавить длину body и IPC stage timings; затем сравнить снижение копирований или другой framing на replay fixture. Транспорт уже сохраняет постоянное соединение; массовая замена его ради абстрактного keep-alive не обоснована. В актуальных coverage metrics отсутствуют network samples: reuse нельзя количественно подтвердить этим счётчиком.

6. **Проверить миграционную согласованность.** В repo есть три retention CHECK, но реальная таблица не содержит CHECK. Сравнить историю миграций и фактический DDL на копии базы; подготовить reconcile migration и сначала валидировать существующие строки. Текущая исправленная финализация совместима с ожидаемыми CHECK. Самовольный db push/migrate не выполнялся.

7. **Согласовать статусные контракты.** Источник P0 — строковые наборы delivery states, расходящиеся между модулями. Общие предикаты и typed sets для accepted, active, retryable и terminal; контрактные тесты producer→consumer и схема→SQL. Старые `SENT/UPDATED` оставить совместимыми при чтении, а основной producer пишет единый актуальный статус.

8. **Разделить «пачка очистилась» и «сообщения исчезли».** `telegramCleared` может отражать успешный Telegram этап при потерянной DB-финализации. Добавить раздельные метрики remote-cleared, receipt-finalized, listing-deleted, skipped-claim и backlog возрастов. Это позволит видеть настоящую повторную работу и многопользовательские удержания.

9. **Ускорять DB только по планам.** База небольшая: `collector_runs` ~30,6 MB/17,5 тыс. строк, `telegram_notifications` ~0,81 MB/~532 строки на момент probe. Счётчики seq_scan накопительные и не доказывают медленный запрос. Сначала EXPLAIN и длительности на рабочей выборке; затем возможные partial/composite indexes cleanup/outbox и уменьшение часто повторяемых health count. Огромный pool, Redis вместо durable journal и слепое добавление индексов не обоснованы.

10. **Lifecycle должен явно завершать управленческие шаги.** При этом выпуске сервисы готовы, но наружный PowerShell helper продолжал ждать поток дочернего процесса. Helper завершён, сервисы оставлены работающими. Финальная проверка и LIVE выполнены отдельно; при первом POST без JSON сервер ответил 415. Следующий этап: supervisor/lifecycle readiness через явные process/status markers и корректные JSON API-запросы; отсутствие зависших handles. Выпуск не должен требовать догадок о состоянии по одному завершению shell.

11. **Runtime-инструкции устарели.** AGENTS ссылается на отсутствующий `create-release.ps1`; фактический путь — `verify-production-build.ps1 -PreserveOutputs` → `accept-release.ps1` после остановки → start → LIVE. Обновить документированные команды и добавить проверку их существования. В AGENTS также заявлен AUTO.RIA 60 с, фактический public сейчас 120 с.

12. **Собирать evidence по текущему релизу.** Старые failed queue jobs и замеры до рестарта не смешивать с новым кодом. В статусе встречались 125 failed observation.replay при `failedRecent=0`: это сохранённая история, её наличие само по себе не причина менять runtime. Сравнивать p95/p99, ошибки и полноту на одинаковых cohorts и с достаточной выборкой.

13. **Карантин доставки требует ясного восстановления.** Outbox комментарий говорит, что flash retries не останавливаются по attempt ceiling, но telegram-service содержит потолок и quarantine. Это не новое подтверждение потери: нужно сопоставить актуальные статусы, фактическую настройку и UI re-arm. Добавить контрактный тест и согласовать комментарий, чтобы будущий аудит не принимал карантин за автоматически бесконечный retry.

14. **Redis lifecycle maintenance CLI.** `listing-retention-cli.ts` вызывает Telegram gate без явного ожидания подключения lazy Redis и закрывает только базу. В дополнительном production run первая операция была отложена из-за `enableOfflineQueue=false`. Следующее улучшение CLI: connect до `--apply`, disconnect в finally, dry-run без Telegram/Redis побочных эффектов; тест холодного старта и корректного завершения процесса. Production worker уже подключает Redis перед работой.

## Что сохраняет скорость и надёжность

Сохраняются сериализация OLX origin, защитный circuit/backoff, Redis global Telegram gate, durable PostgreSQL journal до handoff, accepted receipts, постоянные dedupe tombstones, hot/background разделение и standby leader. Фоновые тяжёлые расчёты остаются после первой реакции. Chromium sandbox и challenge solver в текущем релизе не менялись и не входят в предложенные удаления.

Сокращать следует повторные запросы, неэффективные recovery-попытки, redundant updates и административные ожидания. Перечисленные пункты являются очередью следующих работ; помимо P0 они ещё не внедрены.
