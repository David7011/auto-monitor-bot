# План апгрейда OLX: скорость поиска + полнота (не пропускать объявления)

Дата анализа: 2026-07-17. Приоритет: **OLX**, цель — максимально быстрый поиск и
нулевые пропуски. Документ основан на разборе реального кода worker/api и `.env`.

## TL;DR — 6 главных изменений по убыванию отдачи

| # | Изменение | Что даёт | Тип | Сложность |
|---|-----------|----------|-----|-----------|
| A1 | Адаптивная паг’инация realtime «до пересечения с известными ID» | Гарантия отсутствия пропусков между сканами независимо от всплеска | код | средняя |
| A3 | Подключить приватный фид (сейчас это мёртвый конфиг) | +охват частных продавцов (главная целевая аудитория) | код | низкая |
| A5 | Честный `Retry-After` + короткая умная пауза вместо 15 мин | Не уходить в «тёмное окно» на 15–60 мин из-за одного 429 | код | низкая |
| B3/C1 | Реальный User-Agent + джиттер интервала | Меньше блокировок → меньше пропусков и задержек | конфиг+код | низкая |
| A4 | Сентинел переполнения окна (метрика «возможно пропустили») | Видно, когда realtime не успевает | код | низкая |
| B2 | Интервал OLX 5s → 3s (только вместе с анти-блоком) | −1 сек к средней латентности | конфиг | низкая |

Ключевой вывод по скорости: ниже ~5 сек интервала выигрыш небольшой — доминирует
**задержка индексации самого OLX** (объявление появляется в API через секунды–минуты
после публикации). Поэтому основной приоритет — **глубина за один скан (полнота)** и
**никогда не уходить в блок**, а не гонка за интервалом.

## Как сейчас устроен путь OLX (факты из кода)

1. **Планировщик** (`apps/api/src/modules/monitoring/orchestrator.ts`) просыпается по
   ближайшему сроку источника (`SCHEDULER_MIN_SLEEP_MS=100`, `MAX=1000`). Для OLX
   `nextCheckAt` ставится каждые `LIVE_OLX_INTERVAL_SECONDS=5` c (джиттер `=0`).
2. Ставит job в очередь `collector.run` (lane REALTIME). Воркер берёт её
   (`WORKER_CONCURRENCY_COLLECTOR_RUN=3`).
3. **`processCollectorRun`** (`apps/worker/src/processors/collector-run.ts`) берёт
   Redis-лок `collector-lock:OLX:REALTIME`, строит план поиска (для OLX — **один
   широкий публичный контекст** по всей Украине без query, если у фильтров нет общего
   бренда), вызывает `collector.collect`.
4. **`OlxCollector.collect`** (`apps/worker/src/collectors/olx.ts`): в realtime берёт
   **только 1 страницу**. На каждый гео-scope — 1 запрос к
   `https://www.olx.ua/api/v1/offers?limit=40&offset=0&category_id=108&sort_by=created_at:desc`.
   При сбое API — фолбэк на HTML (`window.__PRERENDERED_STATE__`).
5. `selectOlxCandidates`: дедуп по seen, пропуск известных ID (`knownExternalIds`),
   нормализация только новых, отсечка по `publishedAfter`.
6. Новое → `dispatchListing` инлайн (`FAST_INLINE_LISTING_PROCESSING_ENABLED=true`) →
   фильтры → dedup guard → запись в БД → `sendListingLink` инлайн
   (`FAST_INLINE_TELEGRAM_SEND_ENABLED=true`). Обогащение (рынок/VIN) — фоном.
7. Непрошедшее/известное → `recordPendingObservations` (журнал полноты
   `source_seen_listings`).
8. **Backfill** каждые `BACKFILL_INTERVAL_SECONDS=300` c: до `OLX_BACKFILL_MAX_PAGES=30`
   страниц (~1200 объявлений вглубь), восстанавливает пропущенное.
9. **Observation replay** каждые `OBSERVATION_REPLAY_INTERVAL_MS=30000` c: перепроверяет
   незавершённые записи журнала, догидрачивает карточки OLX по detail-URL.

Итоговая цепочка страховок: realtime (быстро, мелко) → backfill (раз в 5 мин, глубоко)
→ replay (раз в 30 c, чинит незавершённые). Архитектура сильная; узкие места — ниже.

## Раздел A. Полнота — «не пропускать объявления» (высший приоритет)

### A1. Адаптивная пагинация realtime до пересечения с известными ID ⭐ главное

**Проблема.** В realtime берётся **ровно 1 страница = 40 объявлений** (`OLX_API_PAGE_SIZE=40`
захардкожен, `maxPages` для не-BACKFILL = 1). При этом `REALTIME_MAX_CANDIDATES=80` и
`OLX_MAX_NEW_PER_RUN=80` — то есть намерение обрабатывать до 80 есть, но физически
достаётся только 40. Если между двумя успешными сканами (интервал 5 c, а при загрузке
воркера/локах — больше) на OLX по всей Украине опубликовано **больше 40** легковых
авто, «хвост» в realtime теряется и ловится только backfill'ом (до 5 мин позже) или
replay. На пиках категории 108 всплески >40/скан реальны.

**Решение (золотой стандарт для newest-first).** В realtime листать до тех пор, пока на
странице не встретится **уже известный ID** (`knownExternalIds`) ИЛИ не сработает отсечка
свежести (`publishedAfter`) ИЛИ не достигнут разумный предел страниц. Пересечение с
известными = доказательство, что разрыва между прошлым и текущим сканом нет. В тихое
время это 1 страница (как сейчас), на всплеске — автоматически 2–5. Стоимость почти
нулевая, а пропуски между сканами **исключаются вплоть до предела страниц**.

Код почти готов к этому: `knownExternalIds`, `cutoffEncountered` и цикл по страницам уже
есть — не хватает только продолжать листать в realtime по признаку «нет пересечения».

**Правки:**
- `apps/worker/src/collectors/olx.ts`:
  - `selectOlxCandidates` — вернуть флаг `sawKnownId` (встретился ли на странице ID из
    `knownExternalIds`).
  - в `collect` для realtime: заменить `maxPages=1` на цикл «продолжать, пока
    `observedOnPage>0 && !sawKnownId && !cutoffReached && page < OLX_REALTIME_MAX_PAGES`».
- `apps/worker/src/env.ts`: добавить `OLX_REALTIME_MAX_PAGES` (первоначально 5, текущий hot-path дефолт 1) и
  `OLX_API_PAGE_SIZE` (сделать env-настраиваемым, дефолт 50 — см. A2).

### A2. Размер страницы 40 → 50 (минимум, если не делать A1)

Внутренний web-API `/api/v1/offers` практически повсеместно принимает `limit` до **50**
(проверить эмпирически одним запросом). Даже без A1 это +25% глубины на каждый скан
бесплатно. Идеально — вместе с A1: тогда realtime покрывает ~новейшие 100–250 объявлений
за скан на всплесках.

- `apps/worker/src/collectors/olx.ts`: `OLX_API_PAGE_SIZE` → из env, дефолт 50.

### A3. Подключить приватный фид — сейчас это мёртвый конфиг ⭐

**Находка.** В `.env` задан `OLX_EXTRA_SEARCH_URLS` с фильтром `private_business=private`
(только частники). Но функция, которая его читает — `olxFeedUrls()` в `olx.ts:299` —
**не вызывается нигде в рабочем коде**. Реальные запросы строит `olxFeedTargets`, которая
`OLX_SEARCH_URL`/`OLX_EXTRA_SEARCH_URLS` игнорирует. То есть настроенный приватный фид
**не опрашивается вообще**. Широкий фид включает и частников, и бизнес — но отдельный
приватный проход даёт бо́льшую глубину именно по частным объявлениям (обычно это и есть
цель — свежие сделки от собственников).

**Решение.** Добавить в `olxFeedTargets` вариант scope с параметром приватности к API
(точное имя параметра у `/api/v1/offers` уточнить через DevTools — на HTML это
`search[private_business]=private`, у API обычно вида `filter_enum_private_business[0]=private`).
Либо честно удалить мёртвый конфиг, чтобы не вводил в заблуждение. Рекомендую подключить —
это прямой рост охвата целевого сегмента.

### A4. Сентинел переполнения окна (детектор «возможно пропустили»)

Сейчас есть предупреждение только про **слишком короткую** первую страницу
(`OLX_MIN_EXPECTED_PAGE_ITEMS=10`), но нет сигнала про **переполнение**: если за скан все
собранные ID оказались новыми (нулевое пересечение с `knownExternalIds`), это значит, что
окно между сканами переполнилось и часть объявлений мы, возможно, не увидели.

**Решение.** На realtime-скане: если `sawKnownId=false` при непустом результате — писать
метрику/лог `possible_overflow` и (при A1) продолжать пагинацию. Это и есть измеримый ответ
на вопрос «пропускаем ли мы объявления». Достаточно инкремента счётчика + записи в
`collectorRun.semanticWarnings`.

### A5. Не уходить в «тёмное окно»: honor Retry-After + короткая пауза ⭐

**Проблема.** При 429/защите источник ставится на паузу флат-константой:
`RATE_LIMIT_PAUSE_SECONDS=15 мин`, captcha — 60 мин (`collector-run.ts`,
`handleExternalProtection`). Заголовок `Retry-After` парсится в HTTP-клиенте
(`parseRetryAfter`), но **не доходит** до решения о паузе (в OLX-ветке `fetchOlxApiFeed`
он не прокидывается в `BlockedHtmlResult`, а пауза берёт константу). Итог: один
транзиентный 429 гасит **единственный** realtime-фид OLX на 15 минут — большое окно
пропусков при нашем приоритете на OLX.

**Решение:**
- Прокинуть `retryAfterSeconds` из `fetchOlxApiFeed` в результат и в
  `handleExternalProtection` использовать `pause = clamp(retryAfterSeconds, 30 c, 5 мин)`
  вместо флат-15-мин.
- Для realtime OLX снизить дефолтную паузу до 60–120 c с экспоненциальным бэкоффом при
  повторных 429 (recovery-проба и так предусмотрена).
- Файлы: `apps/worker/src/collectors/olx.ts`, `apps/worker/src/collectors/html-utils.ts`
  (тип `BlockedHtmlResult` + `retryAfterSeconds`), `apps/worker/src/processors/collector-run.ts`.

### A6. Проверить предел offset backfill

`OLX_BACKFILL_MAX_PAGES=30 × 40 = offset до 1160`. Внутренний API OLX обычно ограничивает
пагинацию (~offset 1000). Глубокие страницы могут возвращать пусто/ошибку. Проверить
реальный предел и не тратить запросы вхолостую (упереть в ~offset 1000 при page=50 → ~20
страниц). Мелочь, но экономит запросы и снижает риск блока во время backfill-всплеска.

## Раздел B. Скорость — латентность «объявление → Telegram»

### B1. Где реально выигрыш (честный разбор бюджета латентности)

Типовая латентность = **фаза интервала** (0–5 c, в среднем 2.5 c) + fetch (~0.1–0.4 c) +
инлайн-обработка + Telegram (~0.2–0.8 c) ≈ **3–6 c** от появления в API до сообщения.
Плюс **неизвестная задержка индексации OLX** (секунды–минуты), которую мы не контролируем.

Вывод: гонка интервала ниже 5 c даёт всё меньше, потому что задержка OLX доминирует, а
риск блока растёт (а блок = пропуски и большие задержки). Поэтому «скорость» лучше всего
качается через (1) отсутствие блоков и пауз (Раздел C), (2) отсутствие пропусков, чтобы не
ждать backfill (Раздел A), и лишь потом (3) сам интервал.

### B2. Интервал OLX 5s → 3s — только вместе с анти-блоком

Снижает среднюю фазу с 2.5 c до 1.5 c (−1 c к средней задержке). Делать **только** после
B3/C1, иначе повышенная частота на одном IP → 429 → 15-мин тёмные окна (нетто хуже по
полноте). `.env`: `LIVE_OLX_INTERVAL_SECONDS=3`.

### B3. Реальный User-Agent + джиттер ⭐ (дёшево, снимает главный анти-бот триггер)

- `SOURCE_HTTP_USER_AGENT` сейчас = `...AutoMonitorBot/0.2` — прямая подпись бота,
  провоцирует блокировку. Заменить на реальный современный браузерный UA (Chrome/Win),
  лучше — небольшой пул с ротацией по запросу (`source-http-client.ts:requestHeaders`).
- `LIVE_OLX_JITTER_SECONDS=0` → идеально периодичные запросы = лёгкий бот-сигнатур.
  Поставить 1–2 c джиттера.
- Добавить корректные заголовки к API-запросу (`Accept: application/json`, `Referer:
  https://www.olx.ua/...`) — приблизить к настоящему браузеру.

### B4. Микрооптимизации горячего пути (по желанию)

- Пул соединений `SOURCE_HTTP_CONNECTIONS_PER_ORIGIN=4` — при A1/нескольких scope можно 6–8.
- Хоп «планировщик → BullMQ → воркер» добавляет десятки мс. На фоне 3–5 c интервала
  пренебрежимо; трогать не нужно, пока интервал не уйдёт в суб-секунду.
- Инлайн-отправка в Telegram уже включена — это правильно, ничего менять не надо.

## Раздел C. Анти-блокировка и масштаб (обеспечивает и скорость, и полноту)

- **C1. UA-пул + заголовки + джиттер** — см. B3. Самый дешёвый и важный слой.
- **C2. Пул прокси (если решите идти агрессивнее 3 c или ловите блоки).** Ротация
  исходящих IP для запросов к источникам — единственный способ безопасно повысить частоту
  на одном крупном источнике. Крупная задача (нужен провайдер + слой ротации в
  `source-http-client.ts`); закладывать, только если C1 недостаточно.
- **C3. Умные паузы/бэкофф** — см. A5. Короткая пауза + honor Retry-After вместо флата.

## Раздел D. Наблюдаемость (чтобы точно знать, что не пропускаем)

- Метрика **saturation/overflow** (A4): доля realtime-сканов с нулевым пересечением —
  прямой индикатор «окно переполняется, добавь страниц/сократи интервал».
- Дашборд по OLX: `pending`/`failed` из `/observations/summary` в разрезе OLX; средняя
  задержка `publishedAt → firstSeenAt → notifiedAt`.
- Алерт, когда realtime-сканы OLX коалесятся из-за лок-коллизий (сейчас тихо теряется
  каденс под нагрузкой — `retryLockCollision`).
- Считать «глубину backfill»: сколько новых нашёл backfill, которых не видел realtime —
  если стабильно >0, значит realtime-окно мелковато (усилить A1/A2).

## Порядок внедрения (этапами, каждый проверяем на реальном трафике)

1. **Этап 0 (сегодня, конфиг):** реальный UA + джиттер 1–2 c (B3). Замер частоты
   429/захватов до/после.
2. **Этап 1 (полнота, код):** A2 (page 50) + A1 (адаптивная пагинация) + A4 (сентинел).
   Это ядро «не пропускать». Проверить логами overflow и backfill-глубиной.
3. **Этап 2 (анти-тёмные-окна, код):** A5 (Retry-After + короткая пауза).
4. **Этап 3 (охват, код):** A3 (приватный фид) + A6 (предел offset).
5. **Этап 4 (скорость):** B2 (интервал 3 c) — только если Этап 0 показал низкий уровень
   блоков. Дальше — C2 (прокси), если нужен интервал <3 c.
6. **Этап 5:** D (метрики/алерты) — параллельно, для контроля регрессий.

Проверки после каждого этапа: `pnpm typecheck && pnpm lint && pnpm test`, затем наблюдать
`collector_runs`, `/observations/summary`, задержки уведомлений.

## Замечания по безопасности

В `.env` лежат **боевые секреты** (Telegram bot token, ключ AUTO.RIA, пароль БД,
`DASHBOARD_AUTH_SECRET`, `LOCAL_API_TOKEN`). Не коммитить, не класть в ZIP/бэкапы без
шифрования, не отдавать в клиентский JS. При шаринге этого проекта — сначала выкинуть `.env`.
