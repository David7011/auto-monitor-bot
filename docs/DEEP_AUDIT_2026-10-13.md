## 1. Доступность: два часа мониторинг физически не работал

Журнал Windows: Kernel-Power 42, причина `Battery`; сон **02:37:24.490–04:37:56.839 UTC**, пробуждение связано с крышкой. Разрыв realtime: OLX 7 248 с, AUTO.RIA 7 291 с. Это внешняя причина простоя, а не зависший парсер. Дополнительный wake/idle в журнале не следует смешивать с этим длинным перерывом.

Проверенные значения idle sleep AC/DC уже равны нулю. Скрипт [power-policy.ps1](../scripts/power-policy.ps1) настраивает таймауты сна и специально сохраняет battery/lid actions. Повторное обнуление idle timeout проблему питания не решает.

**Решение:** обеспечить постоянно работающий хост и питание; отдельно наблюдать heartbeat с другого устройства/хоста. Проверка внутри спящего ноутбука не способна сообщить о собственном сне. При возобновлении нужен полноценный catch-up обоих источников. Изменения питания и размещения в этом аудите не выполнялись.

**Приёмка:** длительное окно без провалов heartbeat, проверка потери питания/связи и последующего восстановления полноты. Самая большая прибавка к обнаружению сейчас возможна именно здесь.

## 2. OLX recovery открывается по времени завершения вместо времени запуска

Цепочка: [collector-run.ts:465](../apps/worker/src/processors/collector-run.ts#L465) передаёт schedule evidence → [source-search-plan.ts:610](../apps/worker/src/modules/source-search-plan.ts#L610) создаёт `now` после сбора → [source-search-plan.ts:659](../apps/worker/src/modules/source-search-plan.ts#L659) вызывает recovery plan → [olx-outage-detection.ts:45](../apps/worker/src/modules/olx-outage-detection.ts#L45) сравнивает это время с ожидаемым стартом плюс допуск.

Текущий допуск: jitter 4 с + scheduler tolerance 5 с. Обычный скан длится около 9–13 с. Поэтому своевременно начатый скан нередко объявляется пропущенным.

**Доказательство:** из 376 retained OLX jobs 373 сопоставлены с collector runs по близкому времени старта; 150 открыли recovery. Все эти 150 стартовали в пределах допуска, но завершились за его границей. Пример: expected 05:00:49.509, processed 05:00:49.529, finished 05:00:58.840 UTC. Запуск опоздал на 20 мс, а recovery открылся после нормальных 9,3 с работы. Отдельное воспроизведение чистой функции даёт `false` на своевременном старте и `true` после 11 с выполнения.

В более длинном срезе создано 428 OFFLINE_WINDOW: 354 VERIFIED и 74 UNRESOLVED; 427 успешных realtime runs сообщили об открытии окна. **Не утверждается, что все 428 ложные:** в окне был и настоящий сон. Точно показана ложная классификация своевременных запусков в выборке jobs.

**Исправление:** передавать фактическое время начала скана как отдельный факт; разнести задержку запуска, длительность выполнения и реальный провал успешного покрытия. Нельзя просто поднять tolerance или выключить offline recovery: это замаскирует настоящий простой. Существующие окна сохранять до проверки доказательств.

**Приёмка:** своевременные сканы длительностью 11/20/30 с не создают OFFLINE_WINDOW; настоящий поздний старт/сон создаёт окно; crash до успешного завершения не теряет recovery; overlapping windows и frozen anchors продолжают работать. Затем сравнить число новых окон, background requests и возраст старейшего незакрытого окна.

В основном срезе backfill выполнил 1 480 runs / 750 HTTP requests / 0 новых объявлений; coverage — 343 runs / 591 requests / 0 новых. Это повод убрать ложные причины работы, **не основание удалить coverage целиком**. Нулевой newCount не доказывает бесполезность проверки полноты. Измеренного ускорения realtime на 5 с именно от этого исправления пока нет.

## 3. Telegram: быстрый сигнал доступен одному чату, остальные ждут карточки

В системе два фактических получателя. В дополнительном срезе подтверждены девять flash bundles, все для одного chatId. [telegram-service.ts:616](../apps/worker/src/modules/telegram-service.ts#L616) сохраняет owner chat; отправка на [строке 732](../apps/worker/src/modules/telegram-service.ts#L732) также берёт `TELEGRAM_CHAT_ID`. Fan-out быстрого flash на всех subscribers отсутствует.

Для объявления AUTO.RIA, замеченного 04:38:13.051 UTC, первый сигнал подтверждён одному получателю через **2 604 мс**, другому через **28 041 мс**. Разрыв **25 437 мс**. Следующие примеры дают 23,2 / 21,0 / 18,8 с. Для OLX есть 3,5 против 20,1 с. Имена и chatId в обезличенный отчёт не включены.

Параллельно общий send gate на [telegram-service.ts:31](../apps/worker/src/modules/telegram-service.ts#L31) обслуживает получателей, а альбом на [строке 477](../apps/worker/src/modules/telegram-service.ts#L477) добавляет `(photos−1) × 1 100 мс`: 9,9 с для десяти фото. В runtime есть gate waits до 23,9 с. После flash подробные карточки получают тот же приоритет очереди, что и новые первые уведомления: [processors/telegram.ts:43](../apps/worker/src/processors/telegram.ts#L43).

**Исправление:** durable first-signal receipt для каждого получателя; сначала короткая полезная сводка/ссылка всем нужным получателям, затем фото и обогащённые карточки. Подробности уже анонсированного объявления должны уступать ещё не анонсированному. Учитывать очередь/дедупликацию отдельно для `(listing, recipient, phase)` и сохранять общий интервал 1 100 мс. Хвост burst >20 разбивать на последующие быстрые сводки по фактической длине сообщения; сейчас tail получает фиксированную задержку 5 с и идёт карточками.

**Ожидаемый эффект:** устранение существенной части подтверждённых 10–25+ с ожидания в burst; точное значение проверяется после реализации. Не обещается одинаковое время для 100 получателей при неизменном gate.

**Приёмка:** 1/2/20/21/100 кандидатов, несколько получателей, смешанные отказы фильтра; 429, timeout, блокировка одного чата, crash между API acceptance и записью; каждый подходящий ID появляется в первом сигнале, повторный запуск не создаёт лишнюю отправку. Метрика first-signal должна считаться по каждому получателю, включая самого медленного.

## 4. Ошибка первого получателя задерживает последующих

[telegram-service.ts:262](../apps/worker/src/modules/telegram-service.ts#L262): `for ... await sendListingLinkToChat`. Ошибка выходит из цикла. Сохранение receipts раздельное, но исполнение общего job остаётся связанным. Общий retry [lib/queues.ts:66](../apps/worker/src/lib/queues.ts#L66) — exponential с началом 5 с. Пока первый запрос не завершится/не упадёт, следующий не начнётся; после ошибки его запуск переносится на повторную попытку.

**Исправление:** независимые задания/попытки получателей, ограниченная конкуренция и справедливый общий gate; failure одного чата не должен останавливать fan-out. `PERMANENT` исключается из дальнейшей отправки этому чату, но остальные продолжают. Реализовать вместе с пунктом 3, чтобы не переделывать outbox дважды.

Дополнительно reservation [telegram-service.ts:1193](../apps/worker/src/modules/telegram-service.ts#L1193) не проверяет `nextAttemptAt`: прямой queue job может захватить receipt до срока durable backoff. Селектор outbox этот срок проверяет, поэтому поведение зависит от пути запуска. Нужна единая атомарная проверка eligibility в reservation; повтор должен возвращать ближайший разрешённый срок. Это корректность retries и устойчивость к сбоям, а не доказанное ускорение обычной доставки. Уважение backoff иногда намеренно увеличивает интервал попыток, уменьшая бесполезную нагрузку.

## 5. AUTO.RIA public: ограниченная глубина и отсутствие автоматического catch-up

[auto-ria-public.ts:55](../apps/worker/src/collectors/auto-ria-public.ts#L55): одна страница для REALTIME, до трёх для BACKFILL. Но [orchestrator.ts:54](../apps/api/src/modules/monitoring/orchestrator.ts#L54) не включает AUTO_RIA в `BACKFILL_SOURCES`. В обычном public monitoring наличие кода трёх страниц не означает, что scheduler когда-либо их автоматически обходит.

После двухчасового сна часть объявлений могла уйти с первой страницы до следующего опроса. **Число реально пропущенных объявлений не установлено**: нет независимого полного списка источника за это окно. Достоверное утверждение — текущая архитектура не доказывает покрытие этого интервала.

**Исправление:** отдельный bounded public catch-up с сохранённым курсором/перекрытием страниц и общим журналом ID, с продолжением после рестарта. Нельзя считать promoted/refreshed порядок доказанным порядком публикации. Простого добавления AUTO_RIA в set недостаточно: `FIRST_SEEN` fallback сейчас выставляется только для REALTIME ([auto-ria-public.ts:90](../apps/worker/src/collectors/auto-ria-public.ts#L90)); background-кандидаты с неизвестной публикацией могут иначе пройти freshness-фильтр. Нужно явно определить политику «впервые увидели после простоя», не выдавая её за точное время публикации.

**Приёмка:** несколько страниц новых ID за простой, перестановки/реклама, пересечения saved searches, неизвестное время, restart посередине. Сверка множества ID и причин каждого отклонения; достижение лимита страницы означает LIMITED/UNRESOLVED, а не «всё найдено».

## 6. Пятиминутный cooldown смешивает потерянную работу и историческую переоценку

[observation-replay-selection.ts:5](../apps/worker/src/modules/observation-replay-selection.ts#L5) задаёт 5 минут для PENDING/FAILED/MATCHED/DISPATCHED без listing и для пересмотра REJECTED/DUPLICATE при новой ревизии фильтра. Replay вызывается раз в 30 с ([index.ts:188](../apps/worker/src/index.ts#L188)). После записи lastEvaluatedAt и потери queue handoff следующий durable replay может ждать **300–330 с**, плюс обработку очереди. Обычный Bull retry иногда восстановит раньше; речь о сбое, который оставил durable observation без живого job.

**Исправление:** отдельные политики: свежая недоставленная работа получает короткий retry после истечения lease/проверки отсутствия активного задания; историческая переоценка остаётся ограниченной. Новый filterRevision должен инвалидировать cooldown старой оценки в пределах заданного бюджета. Для durable outbox сравнить 30-секундный replay и 120-секундный pipeline recovery, чтобы один путь не оставался медленным запасным вариантом.

**Приёмка:** Redis недоступен после journal commit, worker погиб после lastEvaluatedAt, очередь восстановилась, фильтр изменился, активный slow job ещё жив. Цель — восстановление потерянной свежей работы за 5–15 с после доступности инфраструктуры; это целевой показатель будущего этапа, не текущая гарантия. В текущем срезе зависших новых observations не обнаружено.

## 7. Коллектор может ждать Telegram до следующего HTTP-запроса

Предыдущий этап правильно передал OLX saved-search кандидатов по готовности каждой страницы. Однако [olx.ts:790](../apps/worker/src/collectors/olx.ts#L790) ждёт callback, [collector-run-helpers.ts:314](../apps/worker/src/processors/collector-run-helpers.ts#L314) ждёт inline processing, а [listing-detected.ts:374](../apps/worker/src/processors/listing-detected.ts#L374) — dispatch с deadline 6 000 мс. На AUTO.RIA аналогичный callback ожидается после ingestion страницы.

Когда Telegram медленный и callback получает единственного подходящего кандидата, следующая страница может начать поиск почти на 6 с позже. Нормальная медиана доставки ниже секунды: это **условный** резерв, не выигрыш каждого прохода.

**Исправление:** завершать callback после durable admission кандидатов и запуска ограниченной задачи доставки, не дожидаясь сети Telegram. Сохранить доказательство durable handoff до продвижения search state; ограничить число задач в памяти. Не обрывать неоднозначно завершившийся Telegram request с немедленным повтором — это создаёт дубли.

**Приёмка:** искусственный Telegram delay >6 с, вторая saved-страница стартует без этого ожидания; crash после journal/before queue; отсутствие пропущенного хвоста; прежняя сериализация OLX HTTP сохраняется. Приоритет после переделки первого сигнала: она сама может существенно уменьшить этот эффект.

## 8. AUTO.RIA 60 → 30 секунд: значимый, но отдельный эксперимент

Исправление 120 → 60 уже выпущено. В новом срезе медиана промежутка запусков 60,322 с, p95 64,605 с. Не нужно повторно «чинить 120».

Если объявление равномерно появляется между проверками и сразу доступно в опрашиваемой выдаче, сокращение интервала 60 → 30 с уменьшает среднее ожидание **с 30 до 15 с**, максимальное — примерно на 30 с. Это расчёт при заданных предпосылках, не обещание ускорить индексацию сайта. Текущие четыре HTTP-запроса на цикл дают приблизительно 240 → 480 запросов/час при одном контексте и непрерывной работе. Длительность скана p50 0,745 с / p95 2,281 с позволяет рассматривать эксперимент со стороны локальной производительности; устойчивость источника под новой частотой ещё не проверена.

Сначала устранить задержки Telegram и определить catch-up, затем контролируемо сравнить 60 и 30 с по свежим ID, ошибкам/блокировкам и времени первого сигнала. Более частое чтение только первой страницы не заменяет восстановление пропущенных страниц.

## Что уже работает и не требует повторного этапа

- P0 retention с несовместимыми статусами исправлен: DELIVERED включён в cleanup; dedupe tombstones сохраняются. Остаточные статусные несогласованности перечислены выше отдельно.
- AUTO.RIA public работает на 60 с, а не 120 с.
- OLX recovery уже содержит evidence v2, обработку изменившегося overlap, группировку окон, durable cursor/backoff, retry surviving lease и фикс повторов при отсутствии фонового слота. Новый дефект относится к **созданию** окон, не отменяет эти исправления.
- Передача OLX saved candidates по готовности выпущена. Текущий aggregate parsed→candidate p95 OLX 78 мс, AUTO.RIA 30 мс: этот участок не выглядит следующим источником выигрыша ≥5 с. Это aggregate, а не отдельный p95 каждой saved-ленты.
- OLX foreground/background HTTP уже сериализован и приоритизирован. Увеличение origin concurrency не предлагается.
- В активной конфигурации unknown-policy MAX_COVERAGE; нет основания возвращать обязательный detail/phone перед первым уведомлением.
- Медиану публикация→обнаружение OLX около 16 минут нельзя целиком приписать коду или целиком доказать как indexing lag по имеющимся данным. Source timestamp, обновления и доступность в разных лентах требуют независимых наблюдений. Public AUTO.RIA вообще не даёт доказанного точного timestamp публикации.

## Пересмотренный порядок этапов

1. **OLX: корректное определение пропущенного запуска.** Небольшое отдельное исправление, regression и LIVE-проверка числа ложных окон. Параллельное организационное условие — непрерывное питание/доступность хоста.
2. **Telegram: первый сигнал всем получателям.** Per-recipient outbox, flash fan-out, первый сигнал выше подробностей, независимые retries; единые статусы и eligibility. Главный измеренный резерв десятков секунд.
3. **AUTO.RIA public: восстановление после простоя.** Пагинация, durable cursor, overlap, честная freshness и явный предел доказанного покрытия.
4. **Быстрое восстановление свежей durable работы.** Разделить retry/replay по назначению; проверить аварийные окна и согласовать crash-acceptance со статусами.
5. **Коллектор не ждёт сетевую доставку Telegram.** После durable admission; реализовать, если трассы после этапа 2 всё ещё показывают callback stalls ≥5 с.
6. **Эксперимент AUTO.RIA 30 с.** Только с baseline и сопоставлением ошибок/полноты; ожидаемый математический эффект 15 с среднего polling wait.
7. **Фоновые бюджеты, enrichment, API/панель, SQL/operations.** Брать в работу по измеренному эффекту; не ставить косметическую перестройку раньше исправлений выше.

Для каждого изменения: воспроизведение → ограниченный patch → проверки множества найденных/отправленных ID и ошибок → полный обязательный release gate → измерение до/после с сопоставимой нагрузкой. Успех измерять не только p50: p95/max, самый медленный получатель, возраст backlog, missed IDs и duplicates. «Без ошибок» — критерий тестов и наблюдения, не гарантия отсутствия всех будущих сбоев.
